## Unresolved & False Positives
* **Migration 0009 alone was insufficient — plan never accounted for pre-existing rows using old tier strings**: Task 3's Step 3 verification only checks that migration 0009 contains a single `ALTER TABLE ... ADD COLUMN` and explicitly expects "No `ALTER TABLE` for the 4 tier enum columns" because SQLite's `text({enum})` isn't a real `CHECK` constraint. That's technically true for the *schema* but the plan never flags the *data* consequence: any pre-existing `standards`/`ranks`/`rank_events` rows written under the old `bronze/silver/gold/platinum/diamond` strings would silently break `ordinal()` (returns `TIERS.indexOf(tier) === -1`) and wedge `ratchetPeak`'s comparisons. This gap was caught and fixed outside the plan's 11 tasks, via a follow-up migration `packages/db/drizzle/0010_remap_legacy_tier_strings.sql` (data remap + division clamp for tiers whose division count shrank, e.g. old platinum-III → new expert, which only has 2 divisions). Classify this as a real gap in the plan's completeness, not a false claim in the plan (the plan's literal claims about migration 0009's *content* are accurate) — but worth flagging since a zero-trust read of "Task 3 done" without checking migration 0010 would miss a serious latent data-corruption bug.
* **"218 tests" full-suite figure in `liftr-audit.md` §7.4 (not in the two audited files, but the only place this count appears) is stale**: current `pnpm test` reports 260 tests across 28 files. This isn't a claim inside the plan or spec under audit, and it's plausible the number was accurate at the moment §7.4 was written, before later `engagement-audit-v3` work added the PR hard-block, weekday-flagged-count tracking, and their tests. Flagged as a discrepancy for completeness since it's the only concrete test-count claim discoverable anywhere near this work.
* **Plausibility thresholds in the design spec (§3.2) no longer match the shipped code**: spec text specifies pace fine/max at 12s/4s per set, jump max-severity at 100%, and ceiling multiple at 1.5x. Current `packages/shared/src/rank/plausibility.ts` uses 15s/6s, 75% max-severity, and 1.3x respectively, per an in-code comment crediting a later "engagement-audit-v3 Phase 3" tightening pass. This is not a false positive about whether the *plausibility gate exists* (it does, fully wired, tested, and functioning per the design's core mechanic), but the spec document itself is now stale on the exact numbers if read as a literal current-state reference.
