## Round 1 Confirmed
* **PathChooser step 0**: Live-verified — the mode chooser (`Selbst zusammenstellen` vs `Nach Muskelgruppe vorschlagen lassen`) is the real first screen of the routine wizard, matching agent-2's static-code finding.
* **Fast path for ≤4 exercises**: Live-verified — selecting exactly 4 exercises visibly collapses the wizard from 3 steps to 2 and renders a simplified flat review (inline sets, "Alle Details anpassen" expander, single "Routine speichern" button) rather than the full Arrange editor.
* **Muscle-coverage glance-check**: Live-verified with real chips for 4 requested muscle groups, correctly marking 3 as "abgedeckt" and 1 ("Waden") as "fehlt" in orange.
* **Equipment-substitution copy**: Live-verified specific, non-generic copy naming "Flachbank" and "Schrägbank" respectively for two different substituted exercises in the same routine — this is a strong confirmation since round 1 only inspected the template string in source, and here two different equipment names were correctly interpolated live.
* **Lopsided-distribution warning**: Live-verified by deliberately engineering a 6-vs-3-sets imbalance; the warning appeared exactly on the imbalanced exercise and nowhere else.
* **Drag-to-reorder**: Live-verified with an actual mouse drag gesture (not just DOM order inspection) — the reordered list persisted across wizard steps and after the routine was saved.

## Round 1 Overturned (Round 1 was WRONG)
* **Custom exercise creation "saves without corruption" / "appears in the list afterward" (agent-8, WS-C Tasks 8-9)**: Round 1 verified only that the server/client code paths exist and that automated tests pass (3/3 server tests). Live testing shows the actual user-visible behavior is broken: after creating "Überkopfdrücken Test", the app displays and stores only the machine slug "ueberkopfdruecken-test" as the exercise's name everywhere it is shown (list tile, detail sheet header). A direct API call confirms the server response for this exercise has no field holding the original display name — only `slug` and `nameKey`, both equal to the slugified string. The previously-claimed "umlaut-slug bug fix" is real only in the narrow sense that the slug itself is now correctly transliterated and doesn't crash or mangle bytes — but the broader user-facing bug (custom exercise loses its human-readable name) is new/unfixed and was invisible to round 1's static/test-only verification.

## Newly Discovered Issues
* **Recurring Ionic Vue console exception**: `TypeError: Cannot read properties of null (reading 'insertBefore')` at `removeViewFromDom` (in `@ionic_vue.js`, via `Pn.hasController.dismiss`) fired repeatedly throughout the entire live session — roughly once every 35-90 seconds, independent of what test action was being performed (idle periods included). This indicates some background Ionic overlay/controller (likely a toast, timer, or modal) is periodically trying to dismiss a view whose DOM node has already been removed, unrelated to any specific user action tested here. This is a real, reproducible runtime bug not discoverable by static code review, and was not mentioned in either round-1 source doc.
* **Custom exercise display-name loss** (see Overturned section above) — beyond the slug-vs-name confusion, this means every custom exercise a user creates will show a slug (e.g. "beinpresse-maschine-2" style names) instead of their chosen name throughout the app (list, detail sheet, and presumably anywhere else `nameKey` is used for custom exercises), which is a materially worse UX regression than "occasionally breaks on umlauts."

## Unverified (Needs Further Manual Check)
* **Edit-mode skip of step 0**: Not re-tested live in this pass (would require opening the wizard from an existing routine's edit affordance, e.g. the "⋮" menu on a routine card, and confirming it lands on "Anordnen" directly). Relied on agent-2's static code citation only.
* **Wrist-curl/reverse-wrist-curl coverage-tally edge case**: Not exercised live (would require specifically adding those exercises and confirming no crash), relied on round-1's code-level fallback citation.
* **Whether the custom-exercise name-loss bug also affects the exercise's appearance inside a saved routine** (i.e., does a routine referencing this custom exercise also show the slug instead of a name in the Workout tab / Arrange step) — not explicitly re-checked after the fact, though the Arrange/Review screenshots earlier in this session for built-in exercises all showed proper names, so this is specific to custom exercises and worth a follow-up check.
* **Root cause location** (client-side lookup-key vs. server-side storage) of the custom-exercise name bug was not traced into `packages/server/src/repositories/exerciseRepository.ts` or the client i18n/name-resolution code — this report is based on live behavior and the API response shape only, not a source-code diff.
