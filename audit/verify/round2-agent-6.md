## Round 1 Confirmed
* **Single import button, no duplicate-button regression**: Live DOM has exactly one element matching "import" text at all times (empty state, with runs, mid-import). Round 1's claim (`RunsPage.vue:124-135`, inline comment documenting the original bug) holds live.
* **Success toast on manual save**: Verified with a live, timestamped DOM poll — toast text "Lauf gespeichert." genuinely renders after a real `201` response, not just present in source but dead code.
* **GPX import success path**: A real GPX file imported successfully (`POST /api/runs/import` → 201), the run appeared in the history list, and selecting it rendered a working Leaflet map + replay UI with zero console errors — going further than round 1's static-only verification of this component.
* **Health Connect empty-state gating**: Confirmed both in source (`isHealthConnectAvailable()` requires `Capacitor.isNativePlatform() && platform === "android"`) and live (desktop browser shows no Health Connect text) — the conditional behaves exactly as intended, no broken-conditional leak onto desktop.

## Round 1 Overturned (Round 1 was WRONG)
* **"Manual-entry save gets inline error feedback on invalid data"**: Round 1 verified this purely by reading source (`RunsPage.vue:33,78-99` — `manualError` ref + try/catch) and concluded the plan's requirement was met. Live testing shows the described user-facing behavior does not occur for the most natural interpretation of "invalid data": typing non-numeric garbage into the km/Minuten fields, or leaving them blank, never triggers `submitManual()` at all — the Speichern button stays `disabled` (verified via `btn.disabled === true` in the live DOM) because `canSubmitManual` gates on `Number(...) > 0`. No inline `.error` element ever appears in this scenario (confirmed via `document.querySelectorAll('[class*="error"]')` returning empty after clicking the disabled button). The `manualError`/try-catch path is real code that _would_ fire on a genuine store/network failure (e.g., server 4xx/5xx after a numerically-valid submission), but round 1's claim as phrased ("manual-entry save gets error handling... form values preserved on failure") implies a user-visible failure mode for bad input that does not exist for the obvious blank/garbage-text case — it's better described as "silently prevented" rather than "handled with inline feedback." Field values ARE preserved, but trivially so, since no submission ever occurs.

## Newly Discovered Issues
* **GPX-imported run shows 0.00 km / 0 min despite valid trackpoints with timestamps and coordinates spanning ~3 minutes**: `GET /api/runs/{id}` for the freshly imported test run returned `"distanceM": 0, "durationS": 0` even though the 7 `trkpt` elements have distinct lat/lon (~55m apart each) and `<time>` values 30s apart (total span 3:00). The map/replay UI itself rendered fine (route polyline visible), but the stat tiles under it showed "0.00 km" / "0 min" / "–" pace. This may be an artifact of the minimal synthetic test file rather than a genuine parser bug (e.g., a real device GPX/FIT export might include extensions or a different point count this parser expects) — flagged for manual follow-up with a real device-exported GPX/FIT file, not confirmed as a production defect.
* **km/Minuten manual-entry inputs have no client-side numeric filtering**: Despite `inputmode="decimal"` on both inputs (`RunsPage.vue:142-143`), arbitrary text ("notanumber", "xyz") can be typed and is accepted by the DOM (this is expected — `inputmode` is only a soft keyboard hint, not an input restriction). Not a defect, just worth noting since it's the mechanism behind the "Round 1 Overturned" finding above — the field silently accepts garbage and only the disabled-button state hides the consequence.

## Unverified (Needs Further Manual Check)
* **Manual-entry `manualError` inline-error path on genuine server rejection**: Not exercised — would require forcing a `4xx`/`5xx` from `POST /api/runs` with numerically-valid input (e.g., stopping the server mid-request, or a duplicate/constraint violation), which was out of scope for this pass. Round 1's underlying code claim (try/catch exists, sets `manualError`, doesn't reset fields on catch) is plausible from source but still unconfirmed live.
* **GPX/FIT distance=0 finding above**: needs a real device-exported file (not a hand-authored minimal GPX) to determine whether this is a genuine import-parser bug or an artifact of the synthetic test fixture.
* **Mobile/bottom-nav layout of the Läufe page**: This session tested at a ~1080px desktop-style viewport (sidebar nav). Liftr's primary target is mobile; the Workout/Läufe switcher and import controls were not re-verified at a narrow mobile viewport in this pass.
