# Design Fidelity Report: Workout/Train Screen vs Pulse × Liftoff / Nebula Mockups
**Last Verified:** 2026-09-04
**Verification Status:** Discrepancies Found

## Method note
Live-rendered comparison via claude-in-chrome against:
- `examples/liftr/liftr-directions.html` — Pulse direction, "Train" screen
- `examples/liftr/liftr-liftoff-variations.html` — "Pulse × Liftoff" section, Train screen
- `examples/liftr/liftr-pulse-liftoff-finalists.html` — "Nebula" dark and "Nebula — Light" mockups
- Live app at `http://localhost:5174/workout`, mid-set on an active routine (the real equivalent of the mockups' "Train" screen), both dark and light themes (toggled via Profil → Darstellung → Hell/Dunkel, `data-theme` attribute).

**Environment caveat discovered mid-audit:** the Chrome profile used for this session has the **Dark Reader extension active** (`data-darkreader-*` attributes were found injected into the live app's `<html>` on a full page load). Dark Reader force-repaints pages, including ones that are already correctly light-themed, which produced misleading near-black screenshots for the live app's light mode on a couple of navigations even though `data-theme="light"` and the underlying CSS custom properties (`--bg:#f6f4fb`, `--surface:#ffffff`) were correct. I cross-checked every color claim below against `getComputedStyle` values read via JS (which reflect the app's real, un-repainted CSS) rather than trusting screenshots alone, and eventually got one clean, undistorted light-mode screenshot via client-side (SPA) navigation. Where a value below comes from computed styles rather than a trustworthy screenshot, I've said so.

## Matches
* **CTA gradient hue/stops**: The live app's primary "Satz speichern" button uses the exact same 3-stop gradient as the mockup's Nebula/Pulse×Liftoff CTA: `#2f9fe0 → #8a6dff → #d63aff` (live) vs mockup's `#2f9fe0 → #7c5cff → #d63aff` — effectively identical, confirming the previously-established tokens.css finding shows up correctly on this one interactive element in both dark and light mode.
* **Light-mode base background**: `--bg:#f6f4fb` on the live app matches the mockup's "Nebula — Light" `--bg1:#f6f3fb` almost exactly, and the light "no glow, neutral elevation" intent from the mockup source comment is honored (CTA `box-shadow:none` in light mode is consistent with mockup's own light-mode design decision, not a bug).
* **Corner radius vocabulary**: Cards and buttons are consistently rounded in the 16-22px range in both mockup and live app — no sharp-corner regression.
* **CTA font-weight**: Both use `font-weight:800` on the primary action button.

## Does Not Match / Partial
* **Dark-mode base background is neutral, not violet-tinted**: confirms the prior known finding — `--bg:#0a0c14` / `--surface:#161c2d` render as neutral blue-black on the actual Train-equivalent screen, not the mockup's violet-black (`#1c1a3a`→`#0a0912`). This is visually obvious on screenshot: the live dark screen reads as a generic "dark UI," while the mockup's dark screen reads distinctly violet/purple even in unfilled background areas.
* **No colored glow/shadow anywhere in dark mode**: every interactive/gradient element on the live Train screen (`log-set-btn`, `.rank-progress`, `.badge`, `.level-dot`) computes `box-shadow: none`. The mockup's dark Nebula treatment explicitly gives the CTA `box-shadow:0 12px 26px -8px var(--shadow-strong)` where `--shadow-strong: rgba(214,58,255,0.55)` — a visible magenta glow that mockup screenshots show as a soft halo under the button. This is entirely absent live; the CTA is flat.
* **The Nebula gradient is a minor accent, not the Train screen's dominant identity**: in the mockup, the CTA, the rank-badge/hexagon, and the progress-fill bar all share the same blue→violet→magenta gradient, making it the unmistakable color signature of the whole screen. In the live app, only two elements out of seven gradient-bearing elements found on `/workout` use the Nebula gradient (the CTA button and a small sidebar `.level-dot`); the rank-progress strip, its badge icon, the pause-timer ring, and the XP bar-fill all use an unrelated bronze/amber "tier" gradient (`rgb(138,79,34)`→`rgb(224,138,60)`/`rgb(58,33,9)`). Visually, the first thing a user sees on entering a set (the large "LEHRLING III" card at the top of the screen) is amber/copper, not violet-magenta — the opposite of the mockup's intended read.
* **Rank badge shape**: the mockup's defining "Liftoff" contribution to Pulse×Liftoff was swapping the rank indicator to a hexagon medallion traced in the gradient (`.hex-frame`). The live app's badge is a rounded-square/diamond icon with a bronze sheen — no hexagon, no gradient outline.
* **CTA typography**: mockup CTA text is small, uppercase, letter-spaced (`0.68rem`, `text-transform:uppercase`, `letter-spacing:0.06em`) — a distinct "chunky pill label" voice. Live CTA text is 15px, sentence case, no added tracking — reads as a standard button label, losing the mockup's stylized typographic identity.

## Unverified (Needs Further Manual Check)
* **True default-load light-mode screenshot**: because Dark Reader intercepted rendering on a couple of navigations, I could not get more than one clean, non-repainted screenshot of the live light-mode Train screen (obtained via SPA client-side navigation rather than full reload). The computed-style values I report for light mode are trustworthy (read directly from CSS, unaffected by Dark Reader's custom-property pass-through), but a human should re-check visually with Dark Reader disabled to be certain no other light-mode-only issue is hidden.
* **Pulse (original, pre-Liftoff) Train screen comparison**: only spot-checked against the "Pulse × Liftoff" and "Nebula" finalist versions per the task's chosen lineage; the original solo "Pulse" direction's Train screen (violet-to-mint, not blue-to-magenta) was screenshotted but treated as superseded, per the task framing.
* **Animation/motion parity**: mockups are static HTML with no real interaction states beyond CSS; whether the live app's button press/hover states, progress-bar fill animation, or rest-timer ring animate in a way that matches the mockup's implied "motion-implied polish" was not assessed — this requires interaction, not a single screenshot.
